# Local Dev Recovery Plan

## Scope

Project audited:

```cmd
G:\Sistema de Prospectar Marcos Hilario\Macro Envio Masivo Whatsapp
```

This plan prepares safer local development commands only. It does not run `npm run dev`, `build`, `lint`, scraping, WhatsApp sending, data mutation, deploys, or any `.env` changes.

## Findings

- `package.json` had `dev` set to `next dev`.
- Local dependency `next` is `16.2.6`.
- The installed Next CLI supports `next dev --webpack`.
- The installed Next bundler resolver defaults to Turbopack when no bundler flag is passed. In `node_modules\next\dist\lib\bundler.js`, no bundler flag sets `TURBOPACK=auto`.
- The reported log is consistent with the default `next dev` path using Turbopack on a slow `G:\` filesystem.
- `.next` exists, is ignored by `.gitignore`, and is generated Next output/cache. At audit time it was about 194 MB.

## Added Scripts

The original `dev` script is left unchanged for reference.

```json
"dev": "next dev",
"dev:webpack": "next dev --webpack",
"dev:lowmem": "set \"NODE_OPTIONS=--max-old-space-size=4096\" && next dev --webpack",
"dev:safe": "set \"NODE_OPTIONS=--max-old-space-size=4096\" && next dev --webpack --disable-source-maps --hostname 127.0.0.1 --port 3000"
```

### Script Intent

- `dev:webpack`: bypasses Turbopack by explicitly selecting webpack.
- `dev:lowmem`: uses webpack and raises the Node V8 old-space limit to 4096 MB to avoid the observed heap crash.
- `dev:safe`: most conservative local option. It uses webpack, applies the 4096 MB heap option, disables dev source maps, binds only to `127.0.0.1`, and uses port `3000`.

Note: `--max-old-space-size=4096` is not a memory saver. It gives Node enough heap headroom to avoid the fatal V8 OOM while avoiding Turbopack via `--webpack`.

## Safe Windows CMD Commands

Open Windows CMD and run:

```cmd
cd /d "G:\Sistema de Prospectar Marcos Hilario\Macro Envio Masivo Whatsapp"
```

First try the explicit webpack path:

```cmd
npm run dev:webpack
```

If the prior Turbopack cache or heap crash still affects startup, close the terminal, reopen CMD, then try:

```cmd
npm run dev:lowmem
```

If the machine is still under pressure, use the most conservative script:

```cmd
npm run dev:safe
```

Stop the server with:

```cmd
Ctrl+C
```

## Cache Recovery

`.next` is generated by Next.js and is listed in `.gitignore`:

```gitignore
/.next/
```

It can be deleted as a cache/output recovery step when the dev server is fully stopped. This does not delete source files, app code, `.env`, datasets, or WhatsApp data.

Preferred first cleanup, only the dev cache:

```cmd
cd /d "G:\Sistema de Prospectar Marcos Hilario\Macro Envio Masivo Whatsapp"
if exist .next\dev rmdir /s /q .next\dev
```

Full generated output/cache cleanup:

```cmd
cd /d "G:\Sistema de Prospectar Marcos Hilario\Macro Envio Masivo Whatsapp"
if exist .next rmdir /s /q .next
```

After cleanup, start with:

```cmd
npm run dev:safe
```

## Recovery Order

1. Do not run plain `npm run dev` while diagnosing this issue.
2. Ensure no old `node.exe` or Next process is still running.
3. Try `npm run dev:webpack`.
4. If memory failure repeats, try `npm run dev:lowmem`.
5. If the machine still freezes or starts swapping hard, stop it and clear `.next\dev`.
6. Try `npm run dev:safe`.
7. If the slow filesystem warning remains severe on `G:\`, copy only the project folder to a fast local SSD path such as `C:\dev\Macro Envio Masivo Whatsapp`, keep `.env` handling manual, then run the same safe scripts there.

## Guardrails

- Do not run `npm run build` for this recovery path.
- Do not run `npm run lint` as part of startup recovery.
- Do not modify `.env`.
- Do not run scraping scripts.
- Do not send WhatsApp messages.
- Do not modify datasets or Luma Intelligence files.
- Do not delete source files under `src`, `public`, or project documents.
